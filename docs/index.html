FFT, accelerated: one algorithm, five ways to make it fast

An iterative radix-2 Cooley–Tukey Fast Fourier Transform, written once in serial C++ and then rebuilt with OpenMP threads, MPI ranks, hand-written CUDA kernels and JIT-compiled JAX. Every implementation was timed end to end on the same inputs, from 210 to 226 complex doubles.

The problem

Fast in theory, stubborn in parallel

The FFT computes the Discrete Fourier Transform in O(n log n) instead of O(n2). It is the step that makes things like polynomial multiplication, convolution and spectral analysis cheap. Cooley–Tukey divides and conquers: split the input into even and odd terms, transform each half, then combine them with a "butterfly" that yields two outputs for the price of one.

The iterative form makes the parallel structure plain. A bit-reversal permutation reorders the input, then log2(n) butterfly stages sweep the array in place. Each stage holds n/2 independent butterflies, so the work inside a stage is embarrassingly parallel. The stages themselves are strictly sequential, because stage s + 1 reads what stage s wrote. That leaves 26 synchronisation points per transform at n = 226, whatever hardware you run on.

Each backend handles those synchronisation points differently: barriers, message exchanges or kernel launches. The benchmarks show how much each one costs.

Fair timing

What each benchmark measures

Every implementation is timed from data in host memory to the result back in host memory. The cost of copying the input vector is subtracted. GPU versions pay for their transfers, and JAX's JIT compile is excluded with a warm-up call. Correctness is checked by running FFT then inverse FFT and recovering the input within 10−9.

The approach

Four backends, one baseline

The serial C++ version is the yardstick. It is compiled with -O3 -march=native -ffast-math, computes one twiddle factor per stage and updates it incrementally. Each parallel version keeps the same algorithm and the same fft(a, direction) interface.

Shared memory

OpenMP threads

The bit-reversal indices are precomputed into a lookup table, so the swaps run as a parallel for. Each butterfly stage parallelises its loop over independent blocks with schedule(static).

  • Tested with 1, 2, 4, 8, 16 and 32 threads
  • Each stage ends in an implicit barrier, which turns out to be the main cost
openmp/
Distributed memory

MPI binary exchange

Rank 0 bit-reverses the input and MPI_Scatters n/p elements to each rank. Each rank runs the early stages locally. For the last log2(p) stages it swaps buffers with partner rank XOR (1 << d) via MPI_Sendrecv. Finally MPI_Gather collects the result.

  • Tested with 1 to 32 processes on a single node
  • Each rank holds only 2·n/p elements
mpi/
GPU · hand-written

Custom CUDA kernels

A bit_reverse_kernel gives each thread one index to swap. Then log2(n) launches of butterfly_kernel give each of the n/2 threads one butterfly pair, with its twiddle computed by sincos. The kernel launch boundary replaces the CPU barrier.

  • Block sizes 32 to 1024 on an NVIDIA L4 (58 SMs)
  • Profiled with Nsight Systems and Nsight Compute
cuda/
GPU · compiled

JIT-compiled JAX

The same Cooley–Tukey algorithm is written as array operations. Bit-reversal uses bitwise ops on an index array. Each stage reshapes the array into blocks, builds a twiddle vector and applies the butterfly by broadcasting. @jax.jit lowers the whole thing to XLA.

  • Run on the same L4 GPU, and on CPU for comparison
  • About 40 lines, against about 110 for CUDA

Two different regimes show up. On the CPU, OpenMP and MPI speedups peak and then fall. OpenMP is best at 221, where the 32 MB working set fits in the node's 36 MB L3. Scaling

Why more cores stop helping

At n = 226, 32 OpenMP threads run 4.65× faster than one thread, against an ideal of 32×. MPI manages 2.15×. Little of the code is serial. Every stage is parallel. The limit is the per-stage synchronisation. A barrier model, S(p) = p / (1 + 2(p − 1)α), fits the 32-thread data with α ≈ 0.095 for OpenMP. For MPI it gives α ≈ 0.22, which reflects the extra cost of MPI_Sendrecv over a barrier.

Profiling · Intel VTune

Where OpenMP's CPU time goes

Hotspots, 32 threads, all benchmark sizes. Total CPU time 566.5 s.

Only 31.9% of CPU time is butterfly arithmetic. 54.4% is spent spinning in libgomp barriers. The threading analysis agrees: effective CPU utilisation is 12.4% (5.9 of 48 logical CPUs), and spin and overhead account for 59.1% of CPU time, with zero lock contention.

Profiling · Nsight

What limits the GPU

  • At n = 1024 only 512 butterfly threads launch, too few to fill 58 SMs. This is why the GPU loses to serial at small sizes.
  • Each butterfly reads and writes two complex doubles (32 bytes) for a handful of FLOPs. The kernel is memory-bound, so block size barely matters at scale: at n = 226 the six block sizes are within 3.5% of each other.
  • Kernel launches are cheap enough that log2(n) launches cost far less than log2(n) CPU barriers.
  • JAX on GPU runs 2.2× slower than CUDA at 226. Transfers that go through the Python runtime outweigh XLA's kernel fusion. On CPU, JAX is 8.6× slower than serial C++.

Takeaways

The bottleneck moves with the hardware

  • OpenMP is limited by how often it synchronises. It works best at moderate sizes and 8–16 threads, where each thread's chunk is large enough to cover a barrier's cost.
  • MPI adds scatter, gather and pairwise exchange on top of the stage dependency. On one node it cannot beat shared memory. Its strength would show on problems too large for a single node's memory.
  • CUDA turns each stage into a cheap kernel launch over massive parallelism. The limit becomes memory bandwidth, and the result is the fastest implementation from n = 217 upward.
  • JAX reaches about half of CUDA's speed with roughly a third of the code. It would gain more if the data stayed on the GPU across operations.
